## Ground rules

- **Same player experience.** Rendering, visuals, controls and feel stay as they are today. The game keeps its own Canvas 2D + WebGL2 renderer, and **no game engine or UI framework** is added. TypeScript and Vite are build-time tools only: what runs in the browser is still plain JS, rendered the same way.
- **Behavior must not change during Phases 1–5.** These phases restructure code only. Gameplay changes wait until the migration is done.
- **Keep save compatibility.** The localStorage keys (`mv_*`, save slots, `mv_tblayout_v1`, …) and save formats must keep working, so existing saves still load.
- **Release format: one self-contained HTML file**, opened straight from disk (`file://`), exactly like today. Vite bundles everything (JS, CSS, images, map data) into it with vite-plugin-singlefile.
- **No browser automation on this device.** Claude does not drive browsers or simulate user input here: no Playwright, no headless browser screenshots. Browser-based tests and screenshots run only on the **other device**.
- **How each step is verified on this device:**
  1. `npm run typecheck` and `npm run build` pass
  2. `npm test` (Node unit tests, no browser) passes
  3. in Phase 2, the extracted code is byte-identical to the original
  4. the maintainer opens the built HTML and plays through the changed area (smoke checklist from Phase 0)
- **No git yet.** The maintainer keeps manual backups, so make one before each phase.
- **Keep the Portuguese** identifiers, comments and UI text.

- *Notes:*
  - **Report:** `npm run tools:camadas` (logic in `tools/lib/camadas.ts`) parses the assembled script with the TypeScript parser and binder, so the same capture name reused in different `{ }` blocks counts separately. It writes `docs/camadas.md`, and `npm run tools:camadas -- <name>` prints one chain. It also flags load-time calls or value uses before the last layer, captures used outside their wrapper, and runtime/conditional reassignments. The starting count was **197 functions, 320 wrappers and 34 plain replacements**. That is more precise than the regex count in "Measured starting point". `tests/unit/camadas.test.ts` is a ratchet: after merging, lower `TETO` to the new numbers.
  - **Add-on chains (batch 2):** some functions are a base followed by independent add-ons, where each add-on uses `return` to skip the rest of its own code. Each add-on body becomes a named function that stays in its own module, replacing the wrapper. The merged function calls them in load order and keeps each layer's original `try/catch` around the call. Examples: `moitasGL`, `campNapGL(sl, keep)` and `cordaDraw2D` are called from `armasGLPush`/`armasDraw2D` in `v4.8_armas.js`. When the base's early `return` would skip the add-ons, it becomes an `if` block around the base body. `npm run tools:camadas -- <fn> --texto` prints each layer's whole statement with its line range; the batch-2 edit script replaced those ranges after checking each range's first line.
  - **Dead definitions (batch 3):** when a plain replacement (`fn = function …`) threw away the original definition, the final function starts from the replacement's body. The dead body is deleted. Examples: `invDecor` (v6.5 was replaced by v6.6) and `renderEqSlots` (v4.3 was replaced by v4.5). A labeled `break` keeps a base's early `return true` from skipping the add-ons (`tryAddToInv`).
  - **Automatic merging (`npm run tools:fundir`, logic in `tools/lib/fundir.ts`, tests in `tests/unit/fundir.test.ts`):** it reads each layer with the TypeScript parser and binder. Each layer becomes its BEFORE code, the call to the previous version, and its AFTER code. The merger emits the BEFORE sections from the outermost layer inward, then the original body, then the AFTER sections from the innermost layer outward. It refuses anything it can't prove equivalent: a nested call, `this`/`arguments`/`var` in layer code, a parameter changed before `.apply(this, arguments)`, a return that would skip an outer layer's code or change the returned value, names that would collide or be shadowed, or a layer that shares a line with other code. When the original body returns early while AFTER code exists, or when the returned value matters, the body becomes `<fn>Base`. A plain replacement becomes the new base, and the dead layers before it are deleted. It runs as a dry run by default (`--mostrar` prints the result, `--gravar` writes). The unit tests run synthetic programs before and after the merge and compare their output.
  - **Cuts (second version of `tools:fundir`):** a layer that can't be split into BEFORE/call/AFTER (call nested in `if`/`try`/a callback, called twice or with other arguments, a `return` that would skip an outer layer's AFTER code, a name clash) becomes a cut. Everything below it is merged into a named stage (`<fn>Base`, then `<fn>Base2`…, each preceded by `// etapa de <fn>: <versions>`). The layer stays whole as a function and calls that stage where it used to call `_x`. The layers above it are still inlined around it. The planner retries until the plan holds: a layer-level problem adds a cut, and a clash with the original body turns that body into a stage. A layer whose parameter has another name is renamed inside the layer (`{ t }` → `{ t: text }`). When a body that moves into a stage uses `this`/`arguments`, the call is `.apply(this, arguments)`, allowed only if every layer above it passes them along. Every name used by moved code must be in scope at the definition site (checked with the binder); otherwise the merge is refused. As an extra check, the TypeScript diagnostics for unknown names, use-before-declaration and redeclaration on the assembled script are the same as before Phase 3.

Layers become sections in load order: the outermost (last-loaded) layer's "before" code first, then the inner layers, the base body, and the "after" code from the innermost layer outward. Each section gets a `/* vX — what it does */` comment.
